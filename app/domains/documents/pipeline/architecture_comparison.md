# 첨부 예시와 HYUNGU 구조 비교

2026-11-04. 사용자 첨부 흐름도와 현재 HYUNGU 로컬 코드를 비교했다.
**예시는 그림에 표시된 내용과 사용자의 Docling 사용 설명을 기준으로 한다.**
그림에 없는 내부 처리까지 없다고 단정하거나, 다른 브랜치의 실제 실행 결과로 취급하지 않는다.

현재 그림은 [세로 실행 흐름](assets/pipeline_flow_simple.svg),
[분리한 Skill 패널](assets/pipeline_skills.svg), 상세 기술은 [architecture.md](architecture.md)에 있다.

## 공통점

| 공통 구조 | 의미 |
|---|---|
| PDF·DOCX·XLSX·MD·TXT 입력 | 다양한 프로젝트 산출물에서 콘텐츠를 얻으려는 목적이 같음 |
| Storage + documents 등록 후 백그라운드 처리 | 원본과 문서 ID를 확보한 뒤 시간이 걸리는 파이프라인 실행 |
| Parse → Chunk → Extract → Draft → Verify | 문서 읽기, 모델 입력 분할, 정보 추출, 카드 작성, 검증의 책임 구분 |
| 카드와 근거 연결 | 카드의 주장과 원문 위치·인용을 추적하려는 구조 |
| 검증 후 여러 관점의 카드 임베딩·저장 | 카드의 검색 표현과 영속 저장을 후속 단계로 둠 |
| 실패 경로와 작업 결과 반환 | 처리 오류·완료를 사용자에게 전달하는 흐름 |

## 차이점과 영향

| 비교 항목 | 첨부 예시의 표현 | 현재 HYUNGU | 의미·영향 |
|---|---|---|---|
| 로더 | 사용자 설명상 Docling | PDF=pdfplumber, DOCX=python-docx, XLSX=openpyxl, MD=markdown-it-py, TXT=자체 파서 | 형식별 위치·표·셀·코드 메타데이터를 직접 다루고 공통 IR로 연결. 두 방식의 성능 비교를 수행한 것은 아님 |
| 정규화 | 별도 노드 표기 없음 | Parse와 Chunk 사이 Normalize/DocumentIR 존재 | 블록·근거 ID와 순서·원문 위치를 공통 계약으로 만듦. 예시에 정규화 기능 자체가 없다는 뜻은 아님 |
| 청킹 | 헤딩·표·코드 구조를 고려한 분할 | 제목 경계 + 6000자 소프트 목표, 원자 블록 내부 미분할. 기본 중첩 없음 | 짧은 섹션도 별도 청크가 될 수 있고 큰 표는 목표보다 커질 수 있음 |
| Extract 입력 범위 | 문서 전체에서 경험·근거 추출 | 기본은 청크별 0~N 경험. 소문서 통합 옵션 적용 시에만 문서 전체 블록 전달 | 기본 모드는 청크 밖 근거를 인용할 수 없음. 문맥 분리·교훈 누락을 평가해야 함 |
| 지침 표현 | 흐름도에 단계별 Skill을 따로 표시하지 않음 | S1 추출·S2 작성·S3 검증으로 프롬프트와 코드 검사를 별도 그림에 표시 | 설명을 분리한 것이며 실제 새 Skill 실행기를 구현한 것은 아님 |
| Verify 처리 | 주장 대조 + 문제 필드 제거 + 공개 상태 결정 | 근거·상태 검증 후 pass/retry/reject/needs_review. 필요한 단계 재처리 | 잘못된 필드를 삭제해 통과시키는 방식과 다름. 초안 검증과 DB 활성화 시점을 구분 |
| 임베딩 대상·상태 | active는 4종 임베딩, draft는 임베딩 없이 유지 | 최종 Gate pass 초안에 가능한 관점 최대 4개. active는 저장 요청에서 부여 | 필드 부족 관점은 생략. Embed 전에 active DB 카드가 필요한 것은 아님 |
| 일부 읽기 실패 | 그림상 못 읽은 문서가 있으면 카드 경로를 생략하는 분기 | 문서별 실패 격리. 불완전한 문서의 부분 공개 보류, 다른 정상 문서 처리 | 실패의 영향 범위를 문서 단위로 관리. 임의의 모든 예외를 복구한다는 보장은 아님 |
| 원문 검색용 경로 | embed_chunks → save_chunks 존재 | 현재 HYUNGU 미구현·미연결 | 예시는 카드 생성과 별도로 원문 검색 자료를 남기는 경로가 있음. HYUNGU는 카드 생성·저장 경로에 집중 |
| 저장 | 카드 + 문서 근거 저장 | 카드 + 근거 + 관점별 벡터 + 문서 저장 영수증 RPC | 같은 요청 재사용·부분 실패 롤백을 의도한 SQL. 실제 적용·보장은 DB 검증이 필요 |
| 완료 판단 | 저장 카드 또는 검색 가능한 문서가 없으면 failed | 정상 처리한 카드 0건도 빈 저장 영수증 확인 후 completed 가능. 일부 실패·보류는 partial | 작업 수행 완료와 카드 생성 유무를 구분. 원문 검색 가능 여부가 현재 Job 성공 조건은 아님 |

## 현재 구조의 방향과 남은 점검

HYUNGU는 필드별 사실 상태와 근거를 유지하고, 검증·제한 재처리·문서별 저장 확인을 통해
**제공된 문서에 충실한 지식카드를 생성하는 경로**에 집중한다.
예시에 있는 원문 청크 검색 경로까지 구현 완료한 구조로 보이면 안 된다.
원문 청크 검색이 필요하다면 검색 담당자와 범위·저장·임베딩 계약을 별도로 정해야 한다.

예시의 문서 전체 Extract는 여러 절을 함께 볼 수 있는 표현이지만 실제 품질·비용·입력 한도는
그림만으로 판단할 수 없다. HYUNGU의 청크별 호출도 문맥 단절과 중복·누락 가능성이 있어
독립 교훈 기준에 맞춘 추출·작성 정렬과 반복 평가가 남아 있다.
두 구조 중 어느 쪽이 더 정확하다는 측정 결론은 내리지 않는다.

이번 변경은 실행 그림 단순화·지침 분리·비교 설명이다.
파이프라인 코드·모델·프롬프트·환경·DB·평가 데이터는 변경하지 않았다.
