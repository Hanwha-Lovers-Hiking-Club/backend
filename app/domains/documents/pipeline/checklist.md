# 문서 파이프라인 개발 체크리스트

설계·입출력 계약과 임베딩 구성은 [planning.md](planning.md)를 참고한다.
완료 표시는 구현 또는 확인한 항목에만 한다. 가짜 함수 구현과 실제 저장/그래프 연결을 구분한다.

내부 추출 스키마, Parse/Normalize/Chunk와 독립 가짜 함수를 구현했다.
Extract/Draft도 구현했으며 Verify/Embed/Save 및 전체 graph 연결은 아직 구현하지 않았다.
실제로 확인한 항목만 완료 처리한다.

## pipeline에서 먼저 확인·구현할 항목

- [ ] 상위 service에서 받는 문서 참조와 graph의 반환 결과를 합의한다.
- [ ] `models.py`와 `state.py`의 필드·타입·필수 여부를 정하고 상대 담당자에게 공유한다.
- [x] 3번: 본문 7개의 메타데이터, 기술/키워드 문자열 배열, 근거 ID 참조와 evidence_index를 구현한다.
- [x] 3번: 선택적 문자 위치와 0~N개 독립 경험 목록을 구현한다.
- [x] 3번: 사실 상태·미확인 값·근거 메타데이터·인용 구간을 검증하는 스키마 테스트를 통과한다.
- [x] 4번: 5개 형식의 최소 테스트 문서로 추출 순서·표/코드/로그·원문 위치를 확인한다.
- [x] 4번: DocumentIR와 재현 가능한 블록/근거 ID로 연결하고 원래 파일명을 보존한다.
- [x] 4번: 읽기 실패·텍스트 없는 PDF·빈 콘텐츠·인코딩 문제와 혼합 PDF 경고를 구분한다.
- [x] 4번: 구조 기반 청킹, 원자 블록 보존, oversized 표시와 재실행 시 후속 결과 초기화를 구현한다.
- [x] 4번 재검증: XLSX를 전체 적재하기 전에 제한을 검사하고 공백뿐인 PDF 페이지를 경고한다.
- [ ] 실제 대표 프로젝트 문서로 복잡한 PDF 배치·선 없는 표·특수 글꼴 등의 추출 한계를 평가한다.
- [ ] OCR/비전, 이미지/도표와 특수 문서 구조 처리 범위를 정한다.
- [ ] 문서 제목을 원래 파일명과 동일하게 유지한다. LLM의 제목 수정 결과를 채택하지 않는다.
- [x] 5번: 추출/작성 프롬프트와 구조화 모델, 근거 ID를 원본에 연결하는 코드를 구현한다.
- [x] 5번: 경험별 초안과 생략 사유를 분리하고 Draft 이후 Gate가 읽을 사실 상태/근거를 보존한다.
- [x] 5번: 가설 원인을 확정 본문으로 복사하지 않고 새로 도출한 교훈은 inferred로 표시한다.
- [x] 5번: 가짜 모델·모의 HTTP·파싱부터 초안까지의 연결 테스트를 통과한다.
- [x] LLM_PROVIDER와 EXTRACT_MODEL/DRAFT_MODEL로 Ollama/Anthropic 및 단계별 모델을 교체한다.
- [x] 실제 로컬 .env에 Ollama 설정을 적용하고 .env.example에 두 공급자 전환 예시를 남긴다.
- [x] 공급자별 JSON 스키마 요청·응답 검증, 오류와 유료 API 자동 전환 금지를 모의 HTTP로 확인한다.
- [ ] Ollama 설치·모델 pull 또는 Anthropic 계정 설정 후 대표 문서로 추출·작성 내용과 비용/응답 시간을 확인한다.
- [ ] 6번: VERIFY_RULES_ENABLED/VERIFY_LLM_ENABLED를 실제 Gate 실행 분기에 연결한다. 현재는 설정만 존재한다.
- [ ] DB 필수 필드 구조 검증과 LLM 내용 검증을 나누고 판정 이유를 추적한다.
- [ ] 6번: 제목/요약/교훈을 포함한 초안 주장과 원문을 대조하고 불확실성을 사실로 바꾼 표현을 검사한다.
- [ ] pass/retry/reject/needs_review 분기·원인별 재처리와 횟수 제한을 구현한다.
- [ ] needs_review의 보관/검토 경로를 정하고 검증 통과 active 카드와 구분한다.
- [ ] 카드 저장 함수의 입력·반환값·카드+근거 원자성·재시도 책임을 다른 담당자와 합의한다.
- [x] 독립 가짜 저장 함수를 구현한다. 실제 DB 생성 수 0과 fake 표시를 반환한다.
- [ ] 가짜 저장 함수로 연결을 확인하고 실제 저장 성공과 구분한다.
- [ ] 실제 함수 제공 후 연결을 바꾸고, 저장 실패가 완료/성공으로 보고되지 않는지 확인한다.
- [ ] 8번: 카드·근거·최대 4개 벡터의 부분 실패와 같은 작업 재시도 중복을 처리한다.
- [ ] 카드 0개·일부 문서 실패의 최종 결과 기준을 합의한다.
- [x] 네 가지 임베딩의 관점과 구성 필드를 사용자 설명 및 PDF로 확인한다.
- [ ] 네 관점의 입력 조립·빈 필드 처리·모델·저장 계약을 확정한 뒤 embed 노드를 구현한다.
- [ ] 외부 비용 없는 단위 테스트와 필요한 graph 연결 테스트, Ruff 검사를 수행한다.

## 임베딩 구현 전 결정 항목

- [ ] 빈 필드·불완전 카드의 벡터 생성 조건과 누락 관점 처리.
- [ ] 입력 텍스트의 라벨·필드 순서·길이 제한·템플릿 버전.
- [ ] 임베딩 모델·차원·배치 크기·실패/재시도 정책.
- [ ] 기존 스키마에 없는 네 벡터를 컬럼/별도 테이블 중 어디에 저장할지와 카드 ID 연결.
- [ ] 카드+근거+벡터 저장 실패의 원자성/복구 기준, active 공개 시점.
- [ ] 카드 수정 시 어느 관점을 재계산할지와 변경 감지 기준.
- [ ] 검색 관점 선택·복수 검색 결과 통합·리랭킹. 타 담당자와 연결 계약만 합의.

## 상위 문서 도메인 / 다른 담당자와 연결할 항목

- [ ] documents 담당: 다중 업로드 API, 형식/용량 검증과 Storage 원본·문서 메타 저장.
- [ ] documents 담당: 백그라운드 작업 실행과 진행 상황/SSE 연결 계약. API 경로·응답은 실제 명세와 대조.
- [ ] knowledge_cards 담당: 실제 저장 함수와 카드+근거 저장 결과·오류·원자성 계약.
- [ ] DB/Storage 담당: 실제 버킷 허용 형식·용량·권한과 스키마 적용 상태 확인.
- [ ] 챗봇 담당: 검색 대상 카드 상태와 저장 완료 시점에 관한 연결만 확인. 챗봇 본문은 별도 담당.
- [ ] 문서 제목 정책의 표현 차이를 공유 문서 담당자와 정리한다.

기존 PR 템플릿의 서버 확인·구조 준수·스키마 문서 동기화 체크도 유지한다.
기능 테스트는 실행 결과가 있을 때만 체크한다. 실제 외부 연동 검증과 가짜 테스트 결과를 구분해 보고한다.
