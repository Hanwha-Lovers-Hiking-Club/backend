# 실제 문서 테스트 핸드오프

## 0. 이 문서로 시작하는 법

새 세션에서 이렇게 시작하면 된다: "docs/real-document-test-handoff.md 읽고 작업을 이어가자. 먼저 [해야 할 일 중 하나]부터."
팀장이 에이전트/백엔드 개발 초보라서 **작업 방식(1번)을 꼭 지킨다.** 지금 가장 먼저 정해야 할 것은 7번의 "결정이 필요한 것"이다.

## 1. 작업 방식 (팀장 선호, 지켜야 함)

기본 규칙은 `docs/service-connection-handoff.md` 1번과 같다. 핵심만 다시 적는다.

- **설명은 초보 눈높이로, "어떻게/왜"를 항상 같이.** 결과만 말하지 말고 무엇을 어떻게 했고 왜 그렇게 했는지, 비유와 쉬운 용어로.
- **결정은 선택지로.** 장점/단점/트레이드오프를 적고 추천을 첫 번째로 둔다. 팀장이 "추천대로"라고 하면 그대로 진행한다.
- **한 번에 한 단계씩**, 팀장과 같이. **냉정하게 판단**하고, 모르는 것/확인 못 한 것은 "확인 안 됨"이라고 쓴다. 근거 없이 단정하지 않는다.
- **커밋은 요청받았을 때만, 주제별로 나눠서**, 메시지는 `feat : 한글 간략 설명`. 푸시/PR도 요청받았을 때만.
- 코드 스타일은 ruff(줄 길이 100, **한글은 2칸으로 계산**돼서 주석이 길면 걸린다), 주석은 한글, 임시 단순화는 `ponytail:` 주석.
- DB 스키마 변경은 `sql/`에 SQL을 적고 `sql/tables.sql`, `docs/schema.md`를 같이 고친다. **실제 SQL 실행은 팀장만** 한다.
- 이번에 새로 확인된 팀장 방침:
  - 실제 문서 테스트 데이터는 **DB에 그대로 남기고 팀장이 직접 비운다**(에이전트가 삭제 기능을 만들지 않는다). 대신 지울 ID를 `runs/`에 기록해 둔다.
  - 카드 품질은 **팀장이 직접 원문과 대조**한다(자동 평가는 보조 수단).
  - 문제는 "먼저 조사하고, 반복되면 그때 정리해서 같이 고친다".
  - **프로젝트를 섞지 않는다.** job 하나 = 프로젝트 하나(아래 3번 이유).

### 1단계: 변환 품질 (문서 20개 × md/docx/pdf)
| 형식 | 단어 보존 | 변환 시간 | 평가 |
|---|---|---|---|
| md | 100% (원문 그대로) | 즉시 | 파이프라인이 docling을 거치지 않게 바꿈(아래) |

- PDF 최악 사례: ssafesta 빌드 리포트(긴 파일 경로 표)는 단어 35%, 표 행이 한 칸으로 뭉치고 밑줄이 공백으로 쪼개짐(`FestivalSlot _ 03 _ Combined.asset`). 이미지 위주 README는 70~81%.
- 청크가 500토큰 상한을 넘는 경우: 표 행/코드블록이 긴 문서(vigilantis AWS 스모크 결과, 최대 665토큰). 청크 노드 설계(자르지 않음)대로라 버그는 아니다.

## 5. 마주한 문제 (심각한 순)

### 5-1. 검증(verify)이 사실상 작동하지 않았다 → 개선함 (일부 한계 남음)
- **발견**: 카드 32개가 전부 pass. 진짜 카드를 변조(지어낸 수치 / 지어낸 원인 / 지어낸 결과 / 원문과 반대되는 결정)해서 넣어도 **4개 모두 pass**. 판정 사유도 변조 내용을 언급하지 않는 상투구.
- **원인**: "근거와 일관된가"라는 일반 질문에 모델(gpt-4.1-mini)이 거의 항상 통과시킨다. 입력 누락이 아니라 프롬프트/모델 한계.
- **고친 것** (`pipeline/nodes/verify.py`, `prompts/verify.md`):
  1. 카드의 두 자리 이상 수치·날짜가 근거 문서에 있는지 **코드로 교차검사**(한 자리 수는 개수 표현이라 제외). 실제 카드 32개 오탐 0.
  2. LLM이 **주장마다 원문 문장을 인용하고 성격 라벨**(사실 / 결정 / 추정·예상·가정 / 채택하지 않은 대안 / 원문에 없음)을 달게 하고, **코드가 라벨과 인용으로 pass를 뒤집는다**.
- **결과**: 변조 카드 **4/4 걸러냄**(지어낸 원인은 "근거 문장 없음", 반대 결정은 "채택하지 않은 대안"으로 의미 수준에서 잡음). 실제 카드 32개는 29~30 pass(**오탐 약 6%**).
- **시행착오(같은 길을 다시 가지 않게)**: 인용을 글자 그대로 일치시키라고 하면 정상 카드 32개 중 21개가 탈락했다. 이유는 환각이 아니라 모델이 ·, →, 마크다운 기호를 빼거나, 섹션을 통째로 붙여 넣거나(길이 지시 무시), 요약을 의역해서 인용했기 때문. 그래서 지금 규칙은 ① 비교는 글자·숫자만, ② 300자 넘는 인용은 존재 확인 생략, ③ 인용 불일치는 **절반 이상일 때만** 문제, ④ `lesson`은 원문에 같은 문장이 없어도 정상, ⑤ 비교는 8글자 조각 검색(`difflib.SequenceMatcher`는 긴 한글 문서에서 수 분이 걸렸다).
- **남은 한계**:
  - **비용**: 검증이 카드당 약 2.6초 → 약 9초. 카드 17장이면 검증만 약 150초.
  - 아래 5-2(시제 왜곡)는 검증이 못 잡는다(모델이 "사실"로 라벨링).
  - `rewrite`/`discard`는 지금 둘 다 **카드를 저장하지 않는다**(draft_card로 돌아가는 재시도 루프가 없음). 엄격해질수록 카드가 줄어든다.

### 5-2. 결정 문서의 "예상·추정"을 "확인된 결과"로 쓴다 — **outcome은 해결, 나머지 한계 남음**

**후속 (2026-11-02, 맥 환경에서 진행)**: 데이터셋은 `~/Desktop/한화사랑 데이터셋`(맥, 폴더명에 띄어쓰기)에 있다. 아래 측정으로 크기를 쟀고 `outcome_gate`로 고쳤다. 아래의 원래 기록(시도한 것, 조건 2와의 관계)은 그대로 둔다.
- **측정(ADR 22개 → 카드 19장, 원문과 대조)**: 명백한 왜곡 4장(계획·구현 후순위를 달성처럼, "스키마 반영 필요"→"반영되었다", 근거 없는 "정상 동작함"), 경미 6장(이점을 "~되었고"로), 확인 필요 2장, 정상 7장. 원인은 거의 전부 ADR `Consequences`(이점) 섹션이 `outcome`으로 흘러든 것. 비 ADR 28장(계획서·트레이드오프·트러블슈팅·사례 연구)은 대체로 양호(트러블슈팅 과장 1건: 컴파일 성공→"정상 기동").
- **시도와 결과**: ② extract에 `expected_effects` 칸 분리 → 효과 없고 계획서에서 퇴보, 되돌림. **채택: 문장별 상태 라벨 + 코드 게이트**(`outcome_gate.py`, 상세는 `pipeline-tuning-handoff.md` 1.4). 같은 22개 재측정에서 `outcome` 왜곡 명백 4→0, 경미 6→0, 비 ADR 퇴보 없음.
- **남은 한계**: verify가 "문서가 기대한 효과" 줄을 근거 없음으로 보고 rewrite하는 경우(카드가 줄 수 있음), 라벨 실행별 변동, `context` 왜곡 미측정, 경험당 LLM +2회. 판정은 에이전트 1인이 원문과 눈으로 대조한 것이라 팀장 확인이 필요하다.
- 이 맥에는 `runs/`가 없어 위 측정 결과 폴더(`runs/measure-base`, `measure-nonadr`, `measure-v2`, `measure-v3`)는 새로 만든 것이고 `.gitignore`다.

**(이하 원래 기록)**
- **현상**: ADR·trade-off 같은 결정 문서의 `Consequences`/장점/기대 효과/추정 비용을 카드가 `outcome`이나 `context`에 이미 일어난 일처럼 쓴다.
  - vigilantis ADR-0004: 원문 "이대로 구현하면 가드레일이 자동 원복을 **차단한다**"(가정) → 카드 context "자동 원복과 보안 원클릭 해제가 정상적으로 **작동하지 않았다**", outcome "예외 없이 통과하게 **되었고** 단일 경로로 통일됨". **두 번 돌려도 거의 같은 문장**(재현됨).
  - vigilantis ADR-0010: 원문 "월 약 $130(**추정** …)" → 카드 "월 약 $130으로 **운영 가능**"(추정이 빠짐), 제목도 "설계와 운영 경험".
  - 결정 문서에서 나온 카드 5개 중 최소 3개. 표본이 작아서 **빈도와 심각도는 제대로 재지 못했다**.
- **시도한 것과 결과**:
  - `extract.md`에 이미 "outcome은 확인된 결과만, 기대·예상 효과는 결과가 아니다"가 있다. 거기에 `Consequences`/장점/추정은 결과가 아님, 한정어 유지, 가정을 사실로 바꾸지 말 것 등을 구체적으로 더 적고 `draft_card.md`에도 시제 유지 규칙을 넣어 같은 문서 4세트로 전후를 비교했다 → **효과 없음**(outcome이 여전히 확정형). 증명되지 않은 변경이라 **되돌렸다**.
  - `outcome`을 코드로 비우고 카드를 만들어 보았다(결정 문서 3건) → `outcome`의 왜곡은 사라졌지만, **필수 필드(summary/context/lesson)는 비울 수 없어서** ADR-0004의 context에 왜곡이 남았다.
- **조건 2(조건부 필수 필드)와의 관계**: `problem/cause/approach/rationale/outcome`은 최소 1개만 있으면 되고 나머지는 비워도 된다(DB CHECK + `verify` 구조 검사로 이미 적용 중). 그래서 `outcome`을 비우는 것은 **구조적으로 합법**이다. 하지만 모델은 허용돼도 스스로 비우지 않는다(`outcome` 32/32 채움, cause 2개만 null).
- **심각도에 대한 냉정한 평가**: 지어낸 사실이 아니라 **확신 수준의 어긋남**이다. 근거 발췌문이 카드 옆에 원문 그대로 보이므로 어느 정도 완화된다. 하지만 필드 정의("적용 후 확인된 결과")에는 어긋난다. 이게 결함인지는 **제품 관점의 판단이라 팀장이 정해야 한다**(7번).

### 5-3. 메타 필드 누락
- `department` 32/32 null, `project_name` 28/32 null, `project_date` 22/32 null.
- `department`/`project_name`은 원문에 거의 없는 정보라 대부분 맞게 비운 것이다. `project_date`는 문서 12개 중 11개가 상단이나 파일명에 날짜가 있는데도 비었으니 일부는 **놓친 것**(예: 3jmt 4/4 null, ADR-0004). 단 schale `troubleshooting.md`는 한 문서에서 카드 17장이 나와 헤더 날짜 하나를 17장이 공유하는 구조라 비어 있는 게 오히려 정직하다.
- 우선순위 낮음. 날짜만 파일명·헤더를 프롬프트 맥락으로 주는 방법을 검토.

### 5-4. 큰 문서와 PDF
- **157쪽 로그 문서**(mechadog `field_tests/results/20261006_ppe-xiao/summary.md`): md 기준 청크 490개, extract 입력 **258,095토큰 > `MAX_INPUT_TOKENS` 200,000** → `"추출 입력이 너무 큽니다"`로 **job 전체가 실패**한다. 카드가 거의 안 나올 로그성 문서지만, "큰 문서 한 개가 job을 통째로 실패시킨다"는 사실은 실제다. 맵-리듀스 도입 결정의 근거 데이터.
- PDF는 쪽당 3~4초라 큰 PDF는 분 단위(157쪽 536초). job 타임아웃을 넣는다면 값이 10분이면 걸린다(넣지 않거나 15분 이상).
- PDF 코드블록 소실·표 붕괴는 아직 고치지 않았다(단어 90%대라 카드 생성에는 쓸 만할 가능성. 실제 영향은 PDF 카드 비교로 봐야 함).

### 5-5. 처리 속도
- `draft_card`(경험마다 1회)와 `verify`(카드마다 1회)가 **차례로** 호출된다. 카드 17장이면 draft 142초 + verify 약 150초(검증 개선 후 추정). 병렬화 여지가 크지만 **아직 손대지 않았다**.
- 진행률 숫자(`STEP_PROGRESS`)는 균등 분할이다. 위 시간 구성(draft_card 약 60%)을 보면 실제와 많이 다르다. 조정 필요.

### 5-6. 사소한 것
- 근거 `location`에 문서 제목(첫 H1)이 매번 앞에 붙는다. 예: "ADR-0004: 롤백 런북 3종을 … · Context (배경)". 길고 반복적(기능상 문제는 아님).
- 청크 인덱싱이 soft-fail이라 실패해도 job이 성공으로 보인다. 이번에 kure 한도 버그로 드러났다. 경고를 프론트에 보낼지는 미결정.
- 같은 문서를 다시 올리면 같은 카드가 쌓인다(알려진 한계).
- 모델(gpt-4.1-mini)은 **프롬프트의 구체적 규칙을 자주 무시한다**(길이 제한, 시제 규칙, outcome null). 규칙을 글로 더하는 것보다 **코드 검사/좁은 질문**이 잘 통했다.

**B. 검증을 더 쓸 만하게**

- **토큰 집계**: 노드별 `LLM n회 (입력 토큰 / 출력 토큰)`이 로그에 나온다. kure는 usage를 안 줄 수 있어 임베딩은 횟수만 센다.
- **테스트 작성**: 이 프로젝트는 `pytest-asyncio`가 없다(`asyncio.run` 사용).
- **파일 작성 함정**: 한글/백슬래시가 많은 파일을 파이썬 heredoc의 일반 문자열로 쓰면 이스케이프가 꼬여 파일이 깨진다. 이번에 `verify.py`가 이렇게 깨졌다. **Write 도구를 쓰거나 raw 문자열**을 쓴다.
- **느린 연산 주의**: `difflib.SequenceMatcher`로 긴 한글 문서와 부분 일치를 비교하면 수 분이 걸린다. 조각(shingle) 검색을 쓴다.
- **프로세스 정리**: 파이썬 프로세스를 이름으로 전부 끄는 명령(`taskkill /IM python.exe`)은 다른 작업을 끌 수 있어 차단된다. 자기가 띄운 백그라운드 작업 하나만 정확히 멈춘다.
- **임시 스크립트 위치**: 세션 스크래치 폴더에 두었던 것(`verify_all32.py` 등)은 사라진다. 필요한 것은 `scripts/`로 옮긴다.
