# 지식카드 생성 평가 지침

이 문서는 첫 평가 회차의 규칙이다. 평가 중에는 규칙을 바꾸지 않는다.
바꿔야 하면 변경 사유를 리포트에 남기고 영향을 받는 결과를 다시 채점한다.

## 1. 평가 범위

평가 질문은 네 가지다.

1. 사례를 빠짐없이, 중복 없이 찾는가?
2. 확정, 제안, 가설, 미확인을 구분하는가?
3. 카드가 제공된 문서에 충실한가?
4. 게이트가 나쁜 카드를 막고 좋은 카드를 통과시키는가?

평가는 제공된 문서에 대한 충실도만 판정한다. 문서 밖 사건의 진위는 판정하지 않는다.

이번 회차에서 제외: 형식 비교(pdf, docx), 대형 문서, 반복 실행 안정성, 검색 평가, 품질 점수.

## 2. 데이터 취급

- 저장소는 공개 상태이고 일부 데이터셋은 라이선스가 없다.
- 데이터셋, 실행 결과, 정답표, 판정 결과는 커밋하지 않는다.
  `evaluation/runs/`, `evaluation/labels/`, `evaluation/judgments/`는 Git에서 제외되어 있다.
- 리포트에는 원문을 길게 옮기지 않고 지표, 오류 유형, 문서 키, 짧은 설명만 적는다.
- 라이선스가 없는 데이터셋의 원문을 외부 서비스에 보낼 때는 팀이 허용한 모델만 쓴다.
- 문서 수는 manifest가 아니라 실제 파일을 기준으로 한다.

## 3. 문서 구성

- 전체 18개: 프로젝트 6개에서 3개씩 고른다.
- 프로젝트별 3개는 사례·ADR·측정 기록 중 2개와, 카드 생성 여부가 애매한 문서 1개다.
- 음성 문서는 문서 종류로 정하지 않는다. 읽어서 근거가 부족함을 확인한 뒤 확정한다.
- 조정용은 프로젝트당 1개씩 6개, 평가용은 프로젝트당 2개씩 12개다.
- 같은 사건을 다룬 문서는 조정용이나 평가용 한쪽에만 둔다.
- 분할표는 시험 문서 외의 출력을 보기 전에 확정한다.
- 시험 실행 문서(`ssafesta/webgl-stutter-diagnosis-2026-09-07`)는 조정용 SSAFESTA 몫으로 고정한다.
  이 문서의 정답표에는 `labeled_after_output: true`를 표시한다.

## 4. 정답표

- 평가 단위는 파일이 아니라 사례다. 한 파일에 여러 사례가 있으면 사례별로 작성한다.
- 재현율 계산을 위해 선정 문서의 사례를 빠짐없이 표시한다.
- 각 사례는 `required` 또는 `optional`이다. `optional`은 있어도 없어도 감점하지 않는다.
- 필드는 파이프라인과 같은 7개다: context, problem, cause, approach, rationale, outcome, lesson.
- 필드 상태는 `confirmed`, `proposed`, `hypothesis`, `unknown`, `conflicted` 중 하나다.
- 파이프라인에는 `proposed`가 없다. 제안의 처리는 아래 5.3의 기준으로 채점한다.
- 근거 없는 필드의 정답은 빈값이다. 빈값이 정답일 수 있다.
- 교훈은 원문 명시와 원문에서 도출 가능함을 구분한다.
- 정답 작성자는 파이프라인 출력을 보지 않는다. 파이프라인 출력을 정답으로 쓰지 않는다.
- 문서별 정답표를 다 만들면 `v1`으로 고정한다.

## 5. 채점 규칙

### 5.1 매칭

1. 같은 문서의 사례인지 확인한다.
2. 문제와 조치가 같은지 확인한다.
3. 인용 근거가 맞는지 확인한다.

인용문 겹침만으로 판정하지 않는다. 스크립트는 후보를 만들고 애매한 건은 판정자가 확정한다.
정답 1건에는 카드 1장만 매칭한다. 같은 사례의 나머지 카드는 중복이며 정밀도에서 감점한다.

### 5.2 정답 보정

예상 밖의 타당한 카드가 나오면 카드를 곧바로 정답 처리하지 않는다.

1. 판정자가 원문만 다시 읽고 사례 추가 여부를 결정한다.
2. 추가 건수와 이유를 기록해 정답표 `v2`를 만든다.
3. `v2`로 전체 결과를 다시 채점한다.
4. 리포트에는 `v1`, `v2` 점수를 모두 적는다.

### 5.3 상태 오류

상태 오류는 새 지표를 만들지 않고 주장 지지율의 오류 유형으로 집계한다.

| 오류 유형 | 정의 |
|---|---|
| `status_promotion` | 미확인, 가설, 제안을 카드 표현이 확정이나 완료처럼 서술한다. 주장 지지율에서 오류다. |
| `status_label_only` | 문구에는 "계획", "제안"이 남아 있지만 라벨은 `confirmed`다. 주장 오류가 아니며 별도로 건수만 센다. |

### 5.4 게이트

- 차단은 최종 판정이 `reject` 또는 `needs_review`인 경우다.
- 실제 초안 기준 지표는 재시도 전의 첫 초안으로 계산하고, 재시도 결과는 별도로 기록한다.
- 오류 검출률 = 차단된 나쁜 초안 수 / 나쁜 초안 수
- 오차단율 = 차단된 좋은 초안 수 / 좋은 초안 수
- 분모를 채우려면 통과와 차단을 가리지 않고 모든 첫 초안을 판정한다.
- 판정자에게는 게이트 결과를 보여 주지 않는다.
- 중복 카드 자체는 나쁜 초안으로 세지 않는다. 게이트의 검사 대상이 아니기 때문이다.

### 5.5 오류 주입

- 20개를 원인 확정, 미실행 조치의 완료 표현, 수치 변경, 근거 불일치로 나눈다.
- 카드와 추출값의 형식상 일치는 유지하고 원문 근거 내용은 바꾸지 않는다.
- 근거 불일치는 존재하지만 해당 주장을 뒷받침하지 않는 근거 ID를 쓴다.
- 주입 카드가 목표 검증 단계까지 도달했는지 기록한다. 도달하지 않은 카드는 검출로 세지 않는다.
- 주입 결과는 단위 시험이다. 실제 초안 결과와 합쳐서 보고하지 않는다.

### 5.6 주장 50개

- 최종 통과 카드에서 원자적 주장으로 뽑는다.
- 원인, 조치, 결과, 교훈, 제목+요약에서 각 10개를 뽑는다.
- 특정 필드가 10개 미만이면 전수 판정하고 실제 분모를 쓴다.
- 한 문서의 문장으로 표본이 채워지지 않게 문서별로 분산한다. 추출은 고정 시드로 한다.

## 6. 지표

| 평가 질문 | 지표 |
|---|---|
| 사례 탐지 | 재현율, 정밀도, 사례당 카드 수, 중복 카드 수 |
| 사실 상태 | 필드별 상태 정확도, `status_label_only` 건수 |
| 문서 충실도 | 주장 지지율과 오류 유형별 건수 |
| 게이트 | 오류 주입 유형별 검출 수, 실제 초안의 오류 검출률과 오차단율 |
| 손실 진단 | 정답 인용문이 정규화 결과와 청크에 남아 있는 비율 |
| 실행 | 문서당 토큰, 시간, 완료율 |

초기 경고선은 다음과 같다. 합격 기준이 아니며 표본이 작으므로 일반화하지 않는다.

| 지표 | 경고선 |
|---|---|
| 재현율 | 0.7 미만 |
| 정밀도 | 0.8 미만 |
| 주장 지지율 | 90% 미만 |
| 오류 검출률 | 80% 미만 |
| 오차단율 | 10% 초과 |
| `status_promotion` | 1건 이상 |

## 7. 판정 주체

판정은 AI가 맡는다. 편향을 줄이기 위해 다음을 지킨다.

- 파이프라인에 쓰인 모델(`gpt-6.1-sol`, `gpt-6-luna`)을 판정에 쓰지 않는다.
- 역할마다 새 세션을 쓴다. 정답 작성 세션에는 파이프라인 출력을 주지 않는다.
- 평가 결과를 설계하거나 프롬프트를 조정한 세션을 판정에 쓰지 않는다.
- 판정 프롬프트는 `evaluation/prompts/`의 파일을 그대로 쓰고, 모델과 프롬프트 해시를 기록한다.
- 평가용 판정의 20%는 별도 세션이 독립적으로 다시 판정한다. 일치율을 보고하고,
  불일치는 세 번째 세션이 원문만 보고 결정한다.
- 리포트에는 정답과 판정이 사람이 아닌 AI의 결과임을 명시한다.

## 9. 리포트

- 비율은 `9/13`처럼 분자·분모와 오류 사례를 함께 적는다.
- 사례 기준 점수와 프로젝트별 평균을 함께 낸다.
- 합격 판정보다 고칠 오류를 찾는 데 쓴다.
- 평가용 결과를 본 뒤 프롬프트를 바꿨다면 그 결과는 이번 회차 점수에 넣지 않는다.
